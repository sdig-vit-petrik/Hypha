# hypha 0.4.0 (not released)

Notes collected for the next release line; the summary is written when it is cut.

## Breaking changes and upgrade

- **Inputs with no time limit (#238).** `silence_ms = 0` in a port table is an input
  with no time limit (a ROS timeout of 0.0): `NeverArrived` before its first sample,
  `Usable` from it on, never stale; `Input::untimed()` says so. `advisory` and
  `unsupervised` combine. A trigger may be untimed: it has no fallback of its own, and a
  cycle whose triggers are all untimed runs no fallback. Upgrade: an enabled `advisory`
  input now needs `silence_ms` like any other, or the tag `unsupervised`; one without
  either ran with no limit and now fails `start()` (`missing key 'silence_ms': an input
  needs a limit, 0 for none, or the tag hypha::unsupervised`), and an advisory port
  without a table needs `unsupervised`. Write `silence_ms = 0` where the input had no
  limit on purpose. A `StepHarness` refuses `deliver()` to a port whose table has no
  `silence_ms`. The C ABI is unchanged.

- **Table names of the configuration (#234).** `hypha_config_table_names` is new, the
  names of the tables directly under a prefix (`ConfigView::tables()` in C++); `abi.revision`
  goes from 11 to 12. `hypha_config_list_len`, `hypha_config_list_value` and
  `hypha_config_value` also take the name of an entry, `sensors[1].weights`, so that an entry
  of a table list may hold arrays and lists of its own (0.3.0 refused the file at load:
  `lists inside list elements are not supported`; a list inside a list stays refused, with
  the reason `a list cannot hold a list; put it in a field of a table element`).
- **Services (#132, stage 1b).** A plain node or an `ApplicationNode` serves and calls a
  `.srv`: `Node::advertiseService<Srv>()`, `Node::serviceClient<Srv>()` (with
  `hypha::blocking` for a worker thread, a test or a tool), `hypha::Request`,
  `hypha::Deferred`, `hypha::CallResult` (`hypha/service.h`, `hypha/service_client.h`;
  cpp-api.md §8). Ten C functions are new (`hypha_service_server_create`,
  `hypha_service_server_destroy`, `hypha_request_answer`, `hypha_request_defer`,
  `hypha_request_destroy`, `hypha_service_client_create`, `hypha_service_client_destroy`,
  `hypha_client_call`, `hypha_client_status`, `hypha_client_wait_for_server`);
  `abi.revision` goes from 16 to 17. The SDK ships `std_srvs` (`Empty`, `Trigger`,
  `SetBool`): an application that declared its own `std_srvs` with
  `hypha_generate_messages()` drops that call, as the MRS and Autoware examples did. A
  generated service header gains `TYPE_NAME`.
  `HyphaServiceDesc` carries the definitions of a server's `.srv` halves, which the
  server registers in the schema store. `hypha service list|info|call` (a new tool, link
  `hyservice`) calls a service from the shell with a YAML or JSON request and exits with
  a code per outcome. Each client logs its finished calls as `hypha_msgs/ServiceCall` on
  `<service>/calls` while someone subscribes; `hypha play` does not republish it.
  A `CycleNode` serves and calls through ports, `hypha::Requests<Srv>` and
  `hypha::Calls<Srv>` (`hypha/cycle_service.h`, cpp-api.md §8.5, stage 1c): requests and
  outcomes are inputs of a step and answers and calls leave after it, and a replay with
  services between cycles repeats exactly (FSR-44). Six more C functions
  (`hypha_cycle_bind_server`, `hypha_cycle_bind_client`, `hypha_cycle_requests`,
  `hypha_cycle_next_result`, `hypha_cycle_call`, `hypha_cycle_unread_results`), in the same
  unreleased revision 17. A plain server's `Deferred` answered during a cycle step now leaves
  after that step, and a failed step answers it as failed.

- **Wire frame `IOX7` (#255).** The frame header carries `payload_len`, the message's
  bytes within the sample's slice, in what were four bytes of padding (the header stays 56
  bytes), and the CRC covers it. The magic goes from `IOX6` to `IOX7`: a 0.3.0 and a 0.4.0
  process refuse each other's frames as `InvalidFrame` (interface-specification.md, Wire
  frame). It lets a typed loan send fewer bytes than it reserved.
- **Typed loan (#255).** `hypha_publisher_reserve_frame`, `hypha_loan_shrink` and
  `HYPHA_STATUS_LOAN_LIMIT` are new; `abi.revision` goes from 9 to 10.
- **A reset of a step's inputs (#213).** `clear()` of a `Latest` or `Arrivals` port and
  of a `Transforms` port, in a step, forgets the value and the pending samples the step
  admitted, or the dynamic transforms (the static ones stay), when the step returns; the
  input is `NeverArrived` until a later sample, and `Stale` on its old schedule.
  `hypha_cycle_image_clear`, `HYPHA_CYCLE_CLEAR_INPUT`, `HYPHA_CYCLE_CLEAR_TRANSFORMS` and
  `HyphaCycleBindingHealth.cleared_total` are new (the struct grows by 8 bytes);
  `abi.revision` goes from 14 to 15 (execution-model.md §6.8).
  `testing::StepHarness::cleared(port)` tells whether the last step cleared the port.
- **Zero-copy receive and cycle loans (#255).** `HyphaDelivery` gains `holder`, after
  `transport_age_nanos`: a callback keeps its sample in place with `hypha_delivery_retain`
  and gives it back with `hypha_received_sample_release`, within the subscriber's loan
  budget, which a `WaitSet` subscriber now reports as 1 (`MAX_BORROWED_SAMPLES` − 1: one slot
  stays free for the next delivery). A cycle output lends a slot the step fills in place
  with `hypha_cycle_emission_lend`, `hypha_cycle_emission_send` and
  `hypha_cycle_emission_return`. A cycle input on host time reads a message of 64 KiB or
  more in the subscriber's slot instead of copying it into its history. `abi.revision`
  goes from 15 to 16. In C++: `hypha::View<M>` and `hypha::ViewPtr<M>` (`hypha/view.h`),
  `Subscriber<View<M>>`, `Arrivals<View<M>>`, `Latest<View<M>>`, `Output<M>::loan()`; the
  generator emits `hypha::View<M>` for the seven standard messages whose loaned field is an
  array of bytes. The vendored `point_cloud2_iterator.h` carries one marked edit, a
  `PointCloud2ConstIterator` of a view. `StepHarness::deliver()` and `set()` take the
  message type of a view port.
- **A transform buffer with no node (#248).** `hypha_transform_buffer_create_fed` and
  `hypha_transform_buffer_feed` are new; `abi.revision` goes from 10 to 11.
  `testing::StepHarness::deliver(Transforms&, ...)` and `deliverStatic()` feed a step
  test's `Transforms` port through it; a lookup in a harness step threw before.
- **Clock valid (#213).** `hypha_clock_is_valid` is new (`hypha::isClockValid()`: false
  on a simulated-time node until its clock has a value); `abi.revision` goes from 12 to 13.
- **Newest only (#210).** `HYPHA_CYCLE_INPUT_MODE_NEWEST`, a new value of
  `HyphaCycleBindingOptions.mode`, and the C++ tag `newestOnly` of an `Arrivals` port: ROS's
  `queue_size` 1 chosen by the reader. A newest-only trigger steps on the newest of its
  samples due together (on host time those pending in one turn, under simulated time
  those of one stamp) and counts the others as work-limit drops; `abi.revision` goes from
  13 to 14. Nothing changes for a port without the tag. A ported `twist_mux` that declares
  its velocity triggers `newestOnly` forwards only the newest of the commands of one input
  that wait for its turn, as ROS 1's subscriber of queue 1 does.
- **Application checks in `~/state` (#121).** `hypha_msgs/NodeState` gains `checks`
  (`hypha_msgs/NodeCheck[]`, a new message: `name`, `level`, `message`; the levels are
  those of `diagnostic_msgs/DiagnosticStatus`). Its MD5 changes: `NodeState`
  `912221931c7910c5b8618cd343f7e413` → `5ad5d50b47a38f6f78531bd9cdaca967` (with #232's step times), `NodeCheck` is
  `0171feab5d7c2e8dd822ac42a31ea8e1`, and so is the schema hash of the type. A 0.3.0 tool
  does not read the `~/state` of a 0.4.0 node, and the reverse; a recorded `~/state`
  of 0.3.0 does not decode as the new type (`hypha top` shows such a node without a state).
  The golden list `crates/hypha_msgdef/tests/fixtures/golden_md5.txt` follows.
  `hypha::DiagnosticUpdater` feeds the rows (every task is one), and an `ERROR` or `STALE`
  row makes the node `DEGRADED`; a `WARN` row only shows (cpp-api.md §2.7). A node with no
  checks reports `INPUTS_USABLE` as before. `hypha_node_set_checks` and `HyphaNodeCheck` are
  new in the C ABI; `abi.revision` goes from 17 to 18.
- **Several triggers (#206).** `hypha_cycle_set_trigger` and `Cycle::setTrigger` add a
  trigger on each call instead of replacing the trigger; `abi.revision` goes from 6 to
  7. Under simulated time a triggered step at T waits until every upstream reported T,
  not T − 1 ns (execution-model.md §6.6).
- **A triggered step on simulated time reads its other inputs through its time (#231).**
  A step at T of a triggered cycle, for a trigger sample or a fallback, now holds the
  samples stamped exactly T of its inputs that are no trigger, `Latest` and `Transforms`
  inputs included; they were cut strictly before T and came one step late. The partner
  that one upstream step sends with the trigger sample is therefore in the trigger's step
  in a lockstep replay, as it is on host time since #207, and a match by `header.stamp`
  in the step finds it. A replay of a node that compensated for the late partner sees a
  different input; a rate cycle keeps its strict cut. No C ABI change.
- **Topic names under `/hypha/` (#132).** `/hypha` and every topic name under `/hypha/`
  are the framework's and refused with `InvalidTopic`, except `/hypha/intercept/` (the
  state of `hypha intercept`). 0.3.0 refused only `/hypha` itself. The transport keeps its
  services there, and a topic `/hypha/srv/x` shared the server lock of service `/x`.
  Rename such a topic (`/hypha/text` to `/bridge/text`, for example); a ROS bridge
  route's `hypha_topic` follows the same rule.
- **Node manifest.** `hypha_msgs/IntrospectedCycle.trigger` (a topic) becomes
  `triggers` (a list of topics, in port order), which changes the schema hash of
  `IntrospectedCycle` and of `NodeIntrospection`: a 0.3.0 tool does not read the
  `~/introspection` of a 0.4.0 node, and the reverse; a recorded `~/introspection` of
  0.3.0 does not decode as the new type.
- **A stream for each schema of a topic (#209).** A topic name carries one stream per
  message type and per version of a type (its MD5), each an iceoryx2 service of its own
  named `<topic>@<schema hash>`: a 0.3.0 node and a 0.4.0 node do not see each other's
  topics at all. `HyphaServicePortInfo` gains `schema_hash` and the listing reports each
  stream; `abi.revision` goes from 8 to 9. `subscribeRawOfType` takes a `hypha::RawType`
  instead of a type name, since its MD5 selects the stream. A subscription that names no
  MD5 reads the streams that exist when it is created and no longer creates the topic.
  A frame of another MD5 on a topic is no `schema_mismatch` any more, and two MD5s on one
  name have their own policies (two type names of one definition still share one). `hypha_msgs/RequiredInput` gains `data_type` and `md5`
  and `IntrospectedEndpoint` gains `md5`, which changes the schema hash of `NodeState` and
  `NodeIntrospection` again. The MD5s: `RequiredInput` 36176747… → 30435d9760612081c47a9b675d2b5ef8,
  `NodeState` 3f764952… → 029d88fdad9e1e251e936acef2caa3f1, `IntrospectedEndpoint` ffe5f5ae… →
  5083f17ee1ec38babf25e19e40990950, `NodeIntrospection` f50b4d7b… →
  52d9cd223657ce58a341d3710dd9e3f7. The review rounds added `RequiredInput.other_schemas_checked`
  and `RequiredInput.other_schemas` (`hypha_msgs/TopicSchema[]`, a new message,
  `67f9f8ff0c78fa31752269ba082f283f`), so `RequiredInput` is
  `03d9c09e2155a1201b5ca928b9717fdf` and `NodeState` `912221931c7910c5b8618cd343f7e413`.
  `HyphaSubscriberCounters` gains `other_schemas` (`HYPHA_NOT_CHECKED` before a check): 72
  bytes instead of 64, a layout change inside revision 9, which this line introduces; the
  C++ SDK checks the size at compile time. Every endpoint that names an MD5 now writes its
  stream's record, an empty one without a definition, so the 126-byte limit of a topic name
  that held for an endpoint with a definition holds for one without too (an untyped
  endpoint keeps 238). The graph event also fires when a publisher is created or dropped,
  so every node of a domain wakes once per endpoint at a start; each starts at most one
  refresh round per 100 ms. A refresh opens another stream for a moment and takes one of
  its node slots; a stream keeps 2 beyond its endpoints for that and for the check of its
  record when an endpoint drops, so no endpoint is refused for it. A node start that reclaims a dead node removes the records of the streams
  that are gone.
  built on the earlier definitions sees a node's `~/state` and `~/introspection` carry a
  schema hash it does not know and shows no state or manifest for the node (`hypha node
  info` reads the node registry and is unaffected); a recording keeps the definition it
  was made with.
- **The tools follow each stream of a topic name (#209).** `hypha record` writes one MCAP
  channel for each stream, with its own schema, and records a stream that joins a followed
  name later: a second type or version on a name is no longer dropped with an error, and
  `--sync` no longer fails on it. `hypha play` publishes each stream of a topic on its own
  publisher, and under `--clock` counts the chunk and queue rules per stream. `hypha topic
  echo`, `hz` and `bw` follow every stream of the name, label each when the name has several
  (`# type (md5 start)`, a title line), print a header for each stream under `echo -p`, and
  take `--type` and `--md5` to choose. `hypha top` shows a row for each stream, an input's
  type and MD5, and its `other_schemas` (`not checked`, `none`, or the versions). The ROS 1
  bridge's automatic mode bridges the first stream of a name and says once that it drops the
  others. They follow a stream that appears later on the graph event; the SDK gains
  `BusNode::graph_watch`, `BusNode::subscribe_raw_stream` and `StreamFollower`. A stream
  keeps 2 node slots beyond its endpoints (`max_nodes` + 2) for a probe and a release check.
  A stream that joins a followed name after a recording began is recorded from the moment it was followed, and `hypha record` tells how many samples it sent before (`--sync` fails on them, and on a stream that refuses its subscription); `echo -p` refuses a name with several streams and names them. The counts of `hypha play` and `hypha record` lines are per stream, and `hypha record`
  prints `Following <n> stream(s)` where it printed `Following <n> topic(s)`.
- **`hypha topic list` lists the bus, not the traffic (#178).** It reads the transport's
  service listing once and returns at once: a topic that is advertised and has sent nothing
  is listed with its type, which a node whose topics are silent was not. `--timeout` is
  gone (a script that passes it fails with a usage error; drop it), and `-v` adds each
  stream's publisher and subscriber counts. A line is `name  [type]`, and the MD5 start
  follows the type only when a name has several streams; it was always printed. A bus with no topic prints nothing on standard output and
  `no topics on the bus` on standard error, in place of `(no traffic seen in 1s)`. The SDK's
  `TopicInfo` gains `subscribers`.
- **The step-time distribution in `~/state`, and `hypha topic delay` (#232).**
  `hypha_msgs/CycleState` gains `step_p50_nanos`, `step_p90_nanos` and `step_p99_nanos` (every
  step since the cycle was committed) and `recent_step_p50_nanos`, `recent_step_p90_nanos`,
  `recent_step_p99_nanos` and `recent_step_max_nanos` (the last 10 to 20 seconds), from a fixed
  histogram of 16 buckets per power of two, so a quantile is at most 1/16 above the true
  value. This changes the MD5 of `CycleState`, `46426d6e78c0275d233307b74e03001c` →
  `8a1e15495de6a481cc59e0f7c347de9b`, and of `NodeState`, which holds it,
  `912221931c7910c5b8618cd343f7e413` → `63eeeec206eb9c5994cbd2997f040e65` (`5ad5d50b47a38f6f78531bd9cdaca967` with #121's checks): a tool or a node built on
  the earlier definitions shows no state for a node of this version, and the reverse. The C ABI
  does not change (`abi.revision` stays 11). `hypha topic delay <input> <output>` prints the
  median, the 99th percentile and the worst time from an input topic to an output topic, from
  the frames' send stamps alone, with no decoding.
