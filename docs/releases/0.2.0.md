# hypha 0.2.0

A new release line: the frame checksum is bound to the topic, the C++ SDK reports the
supervision state of an input, and qualification evidence is generated and run in CI.
`abi.revision` stays 1.

## Breaking changes and upgrade

- **Wire format.** The frame CRC-32C starts from the CRC-32C of the topic name (the
  topic code); the frame layout and the magic `IOX6` are unchanged
  ([interface-specification.md](../interface-specification.md), wire frame). A 0.1.0
  process and a 0.2.0 process refuse each other's frames: in a mixed domain every
  sample counts as `integrity.corrupt_payload` and none is delivered.
- **Upgrade.** Rebuild every process of a domain against 0.2.0 and follow
  [release-policy.md](../release-policy.md) §5: stop the domain, install, reset its
  shared memory, start. A rollback to 0.1.0 is the same procedure with the 0.1.0 build.
- **C++ source.** `hypha::BindingHealth` is a struct over the C counts instead of an
  alias of `HyphaCycleBindingHealth`. Code that reads its fields builds unchanged; code
  that names it as the C type must use `hypha::BindingHealth`.
- **Metrics.** `transport.lost_wakes` is gone with the audit; `transport.failed_notifications`
  takes its place in `hypha_node_metrics`.

## Changes

- The frame checksum starts from the topic code: a frame that reaches a subscriber of
  another topic is refused as `CorruptPayload`. 0.1.0 accepted such a frame, as its
  documents stated (insertion outside the design); this is a new detection, not a
  defect fix.
- `bindingHealth()` returns the supervision faults and the ignore flag (`stale`,
  `stagnant`, `ignored`) as `~/state` reports them (#21).
- A qualification report: `scripts/qualify.sh` runs the checks, the Rust and C++
  suites, coverage, Miri, the fuzz targets, ASan with UBSan and TSan, and writes the
  result of every requirement from `docs/traceability.toml`, with the builder image by
  its digest. Its exit status tells a requirement with no test yet and a recorded gap
  (3) from a regression (1).
- CI: the gate on amd64 and a macOS build with clippy on every push and pull request;
  nightly on `develop`, the C++ suite on arm64 and the qualification, its report an
  artifact (#14, #30, #71). The builder image is published once per `docker/` version
  and pulled, not rebuilt in every job.
- iceoryx2 0.10.1, with the one `iceoryx2-cal` patch re-applied (#61). It fixes a
  notification race of 0.10.0 (iceoryx2 #2214) that left a listener silent.
- No polling: the 50 ms `WaitSet` audit that recovered those lost wakes is removed, with
  the 50 ms `/clock` poll on simulated time (#70). An idle node no longer wakes 20 times
  a second; a sample is read when its notification arrives. A failed notification is
  logged and counted as `transport.failed_notifications`.
- Test builds carry no debug info (`[profile.test]`): a quarter of the disk and half
  the link time of a test build; a panic still names its file and line, a backtrace
  names functions only. Other debug builds keep full debug info (#62).
- The builder image pins its tool versions; `scripts/in-image.sh` runs any command in
  it, also on macOS.
- New documents: the safety manual, the failure analysis, the safety plan, the
  dependency assessment, the release policy and the SIL 2 readiness assessment. They
  are a first issue by one author, unreviewed, and claim no compliance.
- The workspace builds, lints and passes its Rust suite on macOS again (#26), a
  development platform without a guarantee.

## Assumptions of use

Stated for the first time: [safety-manual.md](../safety-manual.md) and
[failure-analysis.md](../failure-analysis.md). Every requirement has a class, S or N
([requirements-specification.md](../requirements-specification.md)). Without the audit,
a sample whose notification is lost waits for the next one: AoU-21 asks a safety
function to check that the data of a callback subscription keeps arriving (FM-24).
AoU-22 states the one-thread rule of a `WaitSet` that the C header already gave: a run
that starts while another thread is inside a call on it is not detected (FM-37; detecting
it is #83).

## Qualification

The report of the release commit, `scripts/qualify.sh` in the builder image on amd64,
is attached to the release. Every requirement of class S is verified. Not verified,
each of class N and with its recorded gap:

| Requirement | Class | Reason |
|---|---|---|
| FSR-02 | N | No test measures the publish cost against the subscriber count (#27). |
| NFR-03 | N | No automated latency evidence (#5). |
| NFR-04 | N | No rated-load run (#4, #5). |
| NFR-06 | N | No endurance run (#7). |

Neither the 168 h endurance run of NFR-06 nor the 24 h run of release-policy.md §4
exists yet.

## Platforms

Ubuntu 26.04 on amd64 and arm64, in the builder image. On arm64, CI runs the C++ suite
only; the Rust suite and the qualification run by hand in the builder image for the
release (release-policy.md §3). macOS: build and clippy in CI, no guarantee.

## Support

0.1 receives no further fixes ([release-policy.md](../release-policy.md) §6).
